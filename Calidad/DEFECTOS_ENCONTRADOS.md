# Defectos encontrados por las pruebas

Registro de los errores del código que encontraron las pruebas del [plan](PLAN_PRUEBAS_UNIT_INTEGRACION_E2E.md). Según la regla del plan, **no se corrigen**: se documentan aquí y se decide aparte. Cada caso queda en la suite como `it.failing(...)`, así la suite sigue en verde mientras el defecto exista y Jest avisa cuando alguien lo corrija (entonces hay que cambiar `it.failing` por `it`).

| ID | Componente | Prueba | Qué pasa | Qué espera el plan / contrato |
|---|---|---|---|---|
| DEFECTO-03 | `package.json` · script `lint` | [pruebas.yml](../.github/workflows/pruebas.yml) · job `lint` | `npm run lint` ejecuta `tsc -b tsconfig.build.json --noEmit`, y TypeScript rechaza `--noEmit` en proyectos con referencias (`error TS6310: Referenced project … may not disable emit`). El script falla siempre, sin importar el código. El job `lint` de CI usa `npm run build` (`tsc -b`) mientras tanto: hace el mismo chequeo de tipos. | El plan pide un job `lint` con el `npm run lint` existente (sección 6.1). |
| DEFECTO-02 | `packages/platform/src/persistence/outbox-relay.ts` | [infra.int.test.ts](../packages/platform/test/infra.int.test.ts) · "publica los eventos de una misma transacción en el orden en que se escribieron" | El relay lee los pendientes `ORDER BY creado_en, id`. Los eventos escritos en una misma transacción tienen el mismo `creado_en` (`now()` es la hora de inicio de la transacción), y `id` es un UUID aleatorio (`gen_random_uuid()`). Por eso dos eventos de la misma transacción se publican en orden azaroso: la prueba lo vio de forma intermitente y luego se reprodujo de forma determinista. Afecta a los servicios que usan `OutboxRelay` y escriben varios eventos juntos (p. ej. ms-inventory, ms-order). ms-booking no se ve afectado: usa `EventPublisher` con `evt_id` secuencial. | El comentario del relay dice que publica "en orden" y que un fallo "conserva el orden" (plan 4.2). |
| DEFECTO-01 | `apps/gateway/src/app.ts` | [app.test.ts](../apps/gateway/src/app.test.ts) · "borra el x-internal-principal que mande el cliente" | En una petición **sin credenciales** a `/api/v3/*`, el Gateway reenvía a la Partner API la cabecera `x-internal-principal` que mandó el cliente. `requestContext` copia la cabecera al contexto antes de que `authentication` la borre de `req.headers`, y el proxy usa `context.principalToken`. Con credenciales no pasa, porque el Gateway firma uno nuevo y lo reemplaza. Impacto: quien tenga un token interno válido y todavía vigente (dura 120 s) puede reenviarlo sin autenticarse. | El cliente nunca puede enviar el principal interno; solo lo emite el Gateway (plan 3.2, "Seguridad de cabeceras"). |
